# สเปกการแจ้งเตือนในระบบ (Notifications v1)

> สถานะ: **รอเจ้าของอนุมัติ** · ผู้เขียน: Jim · 2026-10-08 · สัญญา API: `docs/api/openapi.yaml` (tag `notifications`)

## 1. สรุปใน 1 นาที

- ผู้ใช้เห็น **กระดิ่ง** ที่แถบเมนูพร้อมจำนวนที่ยังไม่อ่าน และหน้า `/notifications` รายการแจ้งเตือนของตัวเอง
- v1 เป็น **การแจ้งเตือนในระบบอย่างเดียว** — ไม่มีอีเมล ไม่มี push ไม่มี real-time (หน้าเว็บถามจำนวนใหม่เป็นระยะ)
- การแจ้งเตือนสร้างขึ้น **ในธุรกรรมเดียวกัน** กับการเปลี่ยนสถานะที่เป็นต้นเหตุ → ถ้าการเปลี่ยนสถานะล้มเหลว จะไม่มีแจ้งเตือนหลงเหลือ
- เพิ่ม **ตารางใหม่ 1 ตาราง** เท่านั้น (migration แบบเพิ่มอย่างเดียว) · ข้อมูลตัวอย่าง (seed) ไม่เปลี่ยน
- ปิดงานค้าง G7 (override ต้อง "แจ้งทุกคน") ที่ค้างเป็น TODO ใน packet bl-26-4

## 2. เหตุการณ์ที่สร้างการแจ้งเตือน

กติกาทั่วไป: **ไม่แจ้งคนที่กดเอง** · การเรียกซ้ำที่ไม่เปลี่ยนสถานะ (idempotent) **ไม่แจ้งซ้ำ** · ข้อความเก็บเป็นภาษาไทยที่เรนเดอร์แล้วตอนสร้าง

**หมายเหตุ N6/N7:** ผลที่คณะกรรมการกรอกเอง (ไม่มีผู้รายงาน) ไม่สร้างแจ้งเตือน

## 3. ข้อมูลที่เก็บ (ตาราง `notifications`)

| คอลัมน์ | ชนิด | หมายเหตุ |
|---|---|---|
| `id` | uuid | PK |
| `recipient_user_id` | uuid → `users.id` | ลบผู้ใช้ = ลบแจ้งเตือน (cascade) |
| `type` | text (ค่าตามตาราง §2) | เก็บเป็น text ไม่ใช่ enum ของ DB เพื่อเพิ่ม type ใหม่ได้โดยไม่ต้อง migrate enum |
| `title` | text ≤ 200 | ภาษาไทย เรนเดอร์ตอนสร้าง |
| `body` | text ≤ 1000, null ได้ | เช่น เหตุผลที่ส่งกลับ |
| `link` | text, null ได้ | path ภายในเว็บ (ขึ้นต้นด้วย `/`) ห้ามเป็น URL ภายนอก |
| `read_at` | timestamptz, null ได้ | null = ยังไม่อ่าน |
| `created_at` | timestamptz | |

- index: `(recipient_user_id, read_at, created_at desc)` — ใช้ทั้งนับที่ยังไม่อ่านและเรียงรายการ
- แจ้งเตือน **ไม่เป็นข้อมูลที่ต้อง audit** (การกระทำต้นเหตุถูก audit อยู่แล้ว)

## 4. จุดที่ส่งแจ้งเตือน (สำหรับ Kevin)

- มี `NotificationsService.emit(tx, items[])` ตัวเดียว รับ transaction client ของ Prisma แล้ว `createMany` → ทุก service ใน §2 เรียกภายใน `$transaction` เดิมของตัวเอง (ทุกตัวใช้ `$transaction` อยู่แล้ว)
- `emit` กรองผู้รับซ้ำและตัดคนที่กด (`actor.id`) ออกเอง
- ไม่มีคิว/งานเบื้องหลังใน v1 (จำนวนผู้รับต่อเหตุการณ์มากสุดคือ N9 ≈ ผู้เล่นทั้งสาย ≤ 128 แถว)

## 5. API (ดู openapi tag `notifications`)

| Method | Path | ผล |
|---|---|---|
| GET | `/me/notifications?cursor=&limit=&unread=` | `{ items, nextCursor, unreadCount }` เรียง **ยังไม่อ่านก่อน** แล้วใหม่สุดก่อน · `unread=true` = เฉพาะที่ยังไม่อ่าน |
| POST | `/me/notifications/{id}/read` | 204 · อ่านแล้วกดซ้ำได้ (204) · ของคนอื่น = 404 |

ทุกบทบาทที่ล็อกอินใช้ได้ (เห็นเฉพาะของตัวเอง) · ผู้เยี่ยมชมไม่มีแจ้งเตือน

## 6. หน้าเว็บ (สำหรับ Andy)

- **กระดิ่ง** ในแถบเมนู (sidebar) พร้อมตัวเลขที่ยังไม่อ่าน (เกิน 9 แสดง "9+") · ดึง `GET /me/notifications?limit=1` เพื่ออ่าน `unreadCount` ทุก 60 วินาที + ตอนกลับมาที่แท็บ + หลังเปลี่ยนหน้า
- กดกระดิ่ง → หน้า `/notifications`: รายการ (ยังไม่อ่านเป็นตัวหนา) · ปุ่ม **อ่านทั้งหมด** · กดรายการ → mark read แล้วไปที่ `link` · โหลดเพิ่มด้วย cursor
- หน้าผลประเมินของสมาชิก `/me/assessments/{id}` ยังไม่มี → Andy เพิ่ม (ใช้ `AssessmentDetail` ที่มีอยู่) ก่อนเปิดลิงก์ N1–N4
- ว่าง: "ยังไม่มีการแจ้งเตือน" · ใช้ token ของ Pam (ทั้งโหมดกลางวัน/กลางคืน)

## 7. ข้อสันนิษฐาน

- ไม่มีบทบาท "ผู้ดูแลทีม" ในระบบ (ทีมคือการเป็นสมาชิกเท่านั้น) → N9 แจ้งผู้เล่นในสายแทน (D2)
- ไม่ต้องแปลภาษา: ข้อความไทยอย่างเดียวใน v1
- การถามเป็นระยะทุก 60 วินาทีพอสำหรับ v1 (Droplet เดียว ผู้ใช้หลักร้อย)

## 8. คำถามเปิด

1. N2 "ส่งกลับ" ควรแจ้งสมาชิกไหม หรือแจ้งเฉพาะตอนได้ผล (เพราะสำหรับสมาชิก การส่งกลับคือ "รอต่อ")
2. ควรแจ้งกรรมการสนามตอนถูกเพิ่มเข้าประเภท (`putEventUmpires`) ด้วยไหม (ยังไม่อยู่ในตาราง §2)
3. ควรลบแจ้งเตือนเก่าอัตโนมัติไหม
